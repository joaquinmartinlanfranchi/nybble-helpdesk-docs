Incident Lifecycle 05

The most important section: where an incident is born, what it passes through, and how it ends.

Functional Flows 06

What has to functionally happen when someone does something. Format: Actor → Trigger → Steps → Rules → Result.

F1 · Query resolved by AI — the path the product wants to maximize
Implemented
ActorUser
→
TriggerTypes a question
→
SystemSearches the KB
→
SystemAnswers
→
UserConfirms it helped
→
ResultResolved by AI
Steps
  1. The user writes in the chat. The bot decides which tool to use (there is no fixed pipeline).
  2. It calls searchKnowledgeBase against the tenant's KB and their company's.
  3. If the result exceeds the confidence threshold, it answers using only what the KB returned.
  4. The red "end" button appears. When the user closes the chat, they're asked whether it helped, with Yes / No buttons.
  5. Answers Yes → a closed ticket is logged in the inbox with status Resolved by AI.
Rules
  • The KB is the only data source: “NEVER answer questions using data from this summary — ALWAYS call searchKnowledgeBase.”
  • Confidence threshold 70%; interpretation guide: 0.7+ strong, <0.3 weak.
  • Only counts as Resolved by AI if no escalation occurred.
  • Not answering the helpfulness question also counts as Yes (45 min).
Result

Terminal query, no human cost. Feeds the deflection KPI and the KB matching efficiency metric.

F2 · Escalation to a human
Implemented
ActorBot or User
→
Trigger3 failures, critical keyword, or explicit request
→
SystemGenerates summary + classifies
→
SystemCloses the chat
→
ResultPending in the queue
Steps
  1. One of the three escalation conditions is met.
  2. The bot calls escalateToAgent, generating a summary of the entire conversation (“The user asked about…”).
  3. Triage enriches the incident with priority, category, and module.
  4. The chat closes automatically. The helpfulness question is not shown.
  5. The incident enters the corresponding client's shared queue and shows as Pending in My Queries.
Rules
  • Attempt counter: increments when the KB search returns 0 results or all below threshold. On reaching maxAttempts (default 3, configurable 2–5 per tenant) it forces escalation with reason MAX_ATTEMPTS.
  • Off-topic queries do not increment the counter: they're a separate category.
  • Per-session message cap: on reaching it the bot notifies the user and only offers to escalate or create a ticket.
  • The summary must always be attached: without a description or context, “the ticket created for the agent arrives with no context, and that creates friction.”
Defect

Known bug: when escalating, the prior conversation is cleared and restarted, which breaks history continuity toward the human agent (reported 08/12). LABS-572

F3 · Case pickup (assignment)
Implemented
ActorAgent
→
TriggerClicks “Take Case”
→
SystemExclusive lock in the DB
→
ResultIn Review · “Taken by <agent>”
Rules
  • There is no automatic assignment or routing. All enabled agents share a single "ticket pool" and take cases on demand. Routing by specialty is deferred to post-MVP (BR-039).
  • First click wins. The second agent sees the error message “Taken by <agent name>” and the button updates to the new state at that moment.
  • The inbox is filtered by clientId IN (clients assigned to the agent). An agent with a single assigned client only sees escalations for that client.
  • The queue is sorted by priority: CRITICAL > HIGH > MEDIUM > LOW.
  • Cannot take cases for closed-out tenants or clients.
F4 · Handling and direct resolution
No in-app communication
ActorAgent
→
TriggerReviews the taken case
→
Outside the appContacts via Slack / email
→
SystemRequires resolution time
→
ResultResolved
Steps
  1. Opens the incident (it appears below the list; today you have to scroll).
  2. Reads the user's literal query and the AI summary, plus priority, category, module, client, and contact.
  3. If they need to talk to the user, they do it outside the platform (Slack or email).
  4. Fills in the resolution time (hours and minutes) and marks it Resolved.
Rules
  • Resolution time is mandatory for any of the closing actions.
  • Resolved adds 1 to the “resolved by me” counter. The “resolved with workaround” variant was removed.
  • After every CTA the screen reloads so the action is reflected in the metrics.
Limit

The definition of Resolved says “the agent helps them directly via chat,” but that chat doesn't exist on the platform. In practice the agent can only log hours and change the state. Decision from 08/19: out of scope for V1, documented here.

F8 · Knowledge upload and scope
Implemented
ActorKB Manager
→
TriggerUploads a document
→
DecisionAssigned companies?
→

→
SystemRegenerates the topic summary
→
ResultAvailable with its scope
Scope rule
“if a document is not assigned a company, it is tenant-wide (general access, all companies in the tenant). If it's assigned to one or more companies, its scope is limited to the assigned company/companies.”LABS-517, Hernán Nadotti · QA-verified on 08/12 with two independent isolation tests
Rules
  • Indexing states: PENDING → INDEXING → INDEXED / ERROR, with Indexing / Ready / Error labels visible per document.
  • The topic summary regenerates automatically on any KB modification (upload, Drive sync, state change). The admin can also regenerate it by hand.
  • The summary must contain only topic labels, with no data or numbers — e.g. “paid vacation (15-30 days depending on tenure)” becomes “Vacation policy.” It's a safeguard against the bot answering from the summary.
  • Isolation: KB per tenant in a separate namespace (BR-018, BR-083), refined at the company level by this flow.
Open items

Scope for external sources like Google Drive and per-company indexes: TBD post-POC LABS-576.

F10 · Attachments
In Progress
What was requested

Ideal: being able to upload and paste images at any time, with the bot reading and interpreting them as one more tool for resolution. Minimum acceptable: allow uploading files without the bot using them, but have them stay attached to the incident and visible in its detail view. Requested by the Business Solutions team as vital to selling the desk as a product LABS-515.

What exists today
  • An attachment can be added only after the bot answers the first message.
  • Only via the + button: an image cannot be pasted.
  • The bot does not interpret images, not even screenshots of content that's already in the KB itself.
  • The agent cannot attach anything when returning or resolving LABS-516.
Rule that is defined

Every attachment must record who uploaded it and be visible to any role with permission to view that incident or query. Not yet verifiable.

F11 · Routing to Jira
Implemented
ActorAgent
→
Trigger“Approve and Create in Jira”
→
SystemMaps fields per tenant
→
SystemCreates the ticket and saves the reference
→
UserReceives the ticket number
Rules
  • BR-033 — “Only once the agent approves is the ticket formally created in Jira with all mapped fields. The user receives confirmation with the Jira ticket number.”
  • BR-035 — “The system maps the draft's fields to the Jira fields. The mapping is configurable per tenant (defined during onboarding).”
  • The state name was deliberately chosen to be platform-agnostic: “Escalated to Ticket” was replaced with “created in Jira” to reflect the action regardless of which ticketing tool is used.
  • The ticket relies on the AI-generated summary.
  • This CTA does not open a text box or allow attachments.
Heads up

Communication between the user and the agent for this ticket happens outside the platform (Slack, email, or another separate application) — there is no in-app chat. The only thing recorded on the desk is the resolution time the agent logs, which is what allows the incident's state to be updated.
